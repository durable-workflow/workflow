# Original-unit refund accounting

This optional disposable provider model addresses one charged order whose partial shortage can later become a full cancellation. Pin an `OriginalUnitAmounts` before submitting its exact original direct-capture command to the synthetic payment Journal. The application supplies every original unit's minor amount, including its own tax/shipping/rounding allocation; those amounts must sum exactly to the original charge. No amount is inferred from a later quantity.

For example, an original USD 14.99 capture assigned `[500, 500, 499]` to three original units. An authorized shortage command for unit 2 pays 499 minor units. A later authorized cancellation command for units 0, 1 and 2 pays only the remaining 1000; its observation also identifies unit 2 as covered by the first committed payout. A separately repeated remedy for an already-covered unit creates no additional financial payout. A zero-priced unit can settle with a unit receipt and no external money operation.

Each `UnitRefundCommand` retains the original capture identity, explicit charged-unit allocation, fixed business request key and sorted unit ordinals. Native tasks, attempts, processes and recovery sessions do not select the command key. Reusing that key with changed units or allocation is refused. Another client's credential cannot inspect or execute it. Registration after capture admission is refused. Once a quote is pinned, the older whole-capture `refund` path refuses payment so it cannot bypass unit accounting.

The gateway uses the synthetic provider's own SQLite database, outside workflow replay and outside a caller transaction. Original unit claims, the matching payout and the command outcome commit in one provider transaction. An unresolved original command fences overlapping units. Its explicit refusal or definitive non-execution closes that command; a queued request can be refused without acquiring those units. Another authorized request may then claim eligible units. A closed refused command cannot later resurrect. Fixture `plan()` and `resolve()` methods simulate provider decisions; they are not application authority to invent an outcome.

Positive settlement requires the matching original capture and exact payout receipts. Missing or substituted ownership, allocation, payout or capture evidence is refused. Closed storage rows and lookup absence alone never prove repayment. After an acknowledgement is lost following provider commit, lookup and a repeated original command return the same receipt without another payout. The fresh-process control opens the existing database and reads its original descriptor; it neither installs nor seeds a replacement provider.

This model currently accepts direct captures only. Authorization/capture, bank transfers, COD, advance/balance, native common Order/Payment/Shipment integration, physical returns and replacement policies, and installed upgrade/recovery remain separate unfinished requirements. A passing simulator control does not prove a real payment service, complete #1069, or qualify all 33 customer scenarios.
